# Web-интерфейс magnet-platform — технический план

> Решение Sergey (2026-07-15): полноценный современный web-интерфейс. Стек-рекомендация —
> **FastAPI (бэкенд) + React/Vite/TypeScript (фронтенд)**, поверх готовой схемы `MachineProblem
> → solve_machine_problem`. Слой `webapp/` изолирован — только вызывает `magcore` (научное
> ядро не трогается; нарратив 2.4.2 = «электротехнический решатель + метод», веб = доставка).

---

## 1. Цель и границы

**Цель:** пользователь в браузере задаёт задачу (геометрия + материалы + обмотка + режим),
запускает расчёт, видит результат (поля, демаг, рабочая точка по объёму, момент/ЭДС) —
современно, отзывчиво. Дальше — редактор геометрии и импорт STEP/STL.

**Границы (что НЕ делает веб):** не содержит физики/валидации — только вызывает `magcore`.
Всё научное — в ядре (под оракулами). Веб = форма ввода + оркестрация расчёта + визуализация.

---

## 2. Архитектура

```
Браузер (React SPA)  ──HTTP/JSON──►  FastAPI  ──вызов──►  magcore.fem2d.machines
     ▲  формы, графики                 │  фон. задачи        (MachineProblem → solve)
     └──── PNG/JSON результата ◄────────┘  прогресс
```

### 2.1 Бэкенд — FastAPI (`webapp/backend/`)
- Pydantic-схемы зеркалят `MachineProblem` (геометрия/магнит/сталь/обмотка/режим/решатель);
  валидация переиспользует `MachineProblem.validate()` (не дублируем).
- **Долгие расчёты (2.5 c грубая → минуты тонкая) НЕЛЬЗЯ в синхронном запросе.** Модель
  задач: submit → `job_id`, расчёт в фоновом пуле потоков/процессов, статус по поллингу
  (или WebSocket для живого прогресса). Для одиночного локального пользователя достаточно
  in-process пула + словаря задач (без Celery/Redis).
- Картинки: переиспользуем matplotlib из `pilot/viz` (PNG), отдаём как файлы; интерактив
  (Plotly/WebGL) — этап 2.

### 2.2 API-контракт (этап 1)
| Метод | Путь | Назначение |
|---|---|---|
| GET  | `/api/presets` | пресеты: материалы (ndfeb/smco), сталь, дефолт-геометрия |
| POST | `/api/problems/validate` | проверка постановки → список проблем (пустой = ок) |
| POST | `/api/jobs` | принять задачу → `{job_id}` (расчёт в фоне) |
| GET  | `/api/jobs/{id}` | статус: queued/running/done/error + прогресс |
| GET  | `/api/jobs/{id}/result` | `MachineSolution` как JSON (момент, K_e, демаг, раб. точка) |
| GET  | `/api/jobs/{id}/figures/{name}` | PNG (b_field / risk / operating_point) |
| POST | `/api/geometry/import` *(этап 3)* | загрузка STEP/STL → gmsh → mesh + список областей |

### 2.3 Фронтенд — React + Vite + TypeScript (`webapp/`)
Заполняем размеченный скелет:
- `webapp/app/` — оболочка, роутинг, layout, тема (свет/тёмная).
- `webapp/components/` — общие: поля формы, метрик-карты, панели графиков, прогресс.
- `webapp/scene-editor/` — постановка задачи (этап 1: параметрическая форма + живая SVG-схема
  сечения; этапы 3–4: canvas-редактор + импорт STEP/STL + назначение материалов кликом).
- `webapp/result-viewer/` — дашборд результата (метрики + картинки полей/риска/раб. точки).
- `webapp/optimization-ui/` — Часть IV (позже).
- UI: Tailwind + лёгкий набор компонентов (напр. shadcn/ui); графики этап 2 — Plotly/Recharts.
- Dev: `uvicorn` + `vite` с прокси `/api`; прод: сборка React → статика, раздаётся FastAPI.

## 3. Экраны MVP (этап 1)

**(1) Постановка задачи** (`scene-editor`) — левая панель, секции:
- Геометрия: n_slots/n_poles, радиусы/толщины, mesh_size + **живая SVG-схема сечения**
  (кольца статор/зазор/магниты/ротор, обновляется при вводе).
- Материал: магнит (пресет NdFeB/SmCo/custom + даташит-поля Br/Hcb/Hk/Hcj/α/γ), сталь (M270).
- Обмотка: turns_per_slot (раскладка фаз считается автоматически — звезда пазов).
- Режим: сценарий S1/S3, T, i_peak, γ, тумблер «оценить падение ЭДС/момента».
- Инлайн-валидация (несогласованный ввод — сразу подсвечен). Кнопка «Рассчитать».

**(2) Результат** (`result-viewer`) — правая область:
- Метрик-карты: Момент [Н·м], K_e=K_t, сходимость, % за коленом, падение ЭДС/момента.
- Карта рабочей точки: **B_d [Тл]** (среднее/мин по кромке), H_d, P_c, колено, доля объёма за коленом.
- Картинки (вкладки/сетка): |B|, карта риска демага, рабочая точка H_op по объёму.
- Состояние «идёт расчёт» с прогрессом.

## 4. Поэтапный план

| Этап | Содержание | Результат |
|---|---|---|
| **1. MVP** | FastAPI (задача→фон→результат+PNG) + React-форма по `MachineProblem` + дашборд | рабочий веб: задал → посчитал → увидел |
| 2 | интерактивные графики; **библиотека материалов** (свои магниты, save/load JSON — сходится с «контрактом после P4»); свип γ (worst-case); сравнение NdFeB/SmCo | инженерный инструмент |
| 3 | импорт **STEP/STL** (gmsh на сервере) + назначение материалов областям кликом | CAD-ввод |
| 4 | **графический редактор** сечения (рисование/параметрика на canvas) | полный редактор |
| позже | `optimization-ui` (Часть IV: суррогат+CP) | оптимизация в вебе |

**Сначала — только Этап 1** (переиспользует всё готовое). Этапы 3–4 (дорогие, риск дрейфа
в САПР) — отдельно, лучше после/параллельно научному ядру S2, чтобы не съесть его время.

## 5. Технические риски и решения
- **Отзывчивость при тонкой сетке** → фоновые задачи + прогресс; дефолт грубая сетка; в
  перспективе **разреженный решатель** (сейчас плотный, verification-scale) — законная
  инженерная задача, не САПР-дрейф.
- **Изоляция** → `webapp/` только импортирует `magcore`; удаление `webapp/` не трогает ядро.
- **STEP-импорт** → сервер-сайд gmsh (умеет STEP/IGES) проще браузерного парсера; сложная
  часть — интерактивное назначение материалов областям (этап 3).
- **Диссертация** → веб = практическая значимость / акт внедрения, НЕ научная новизна;
  держать компактным, приоритет — S2 (К6′) и метод (суррогат+CP).
